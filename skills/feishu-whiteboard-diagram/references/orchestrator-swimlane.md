# 纵向职责泳道：编排者主链

用于一个编排者串起准入、取数、加工、候选、决策与打包，同时需要说清多个角色交换什么。骨架名为 `orchestrator-swimlane`：角色分列，编排者主链向下，跨职责请求与响应横向展开。

模板固定信息结构与连线语义，不固定角色数量、列宽、配色、业务名称或装饰。实际事实仍来自正文。

## 先判断是不是这张图

| 阅读任务 | 选择 |
|---|---|
| 一个编排者如何组织多个服务，并保留主链与请求 / 响应 | 本骨架 |
| 多角色沿共同时间轴握手，没有中央编排主链 | 普通[泳道](grammars.md#泳道--多角色怎么握手) |
| 来源 → 分析 → 行动的横向价值链，含回流或直达 | [语义分区](semantic-columns.md) |
| 精确的消息先后、条件 fragment、重试或循环 | Mermaid / PlantUML 时序图 |
| 多判断、多回路，需要原生菱形和自动分支布局 | DSL `dagre` / `diamond` |

本骨架的纵向位置表达**编排主链阶段**，不是所有 lane 共享的全局精确时序。跨 lane 对齐只用于组织走线，不能据此推断同步、并发或耗时。

## 构图契约

下面是通用 fixture 的示意事实，不是可套用到实际系统的业务断言：

```yaml
thesis: 编排者把跨服务取数、候选决策与展示打包串成一条主链
grammar: orchestrator-swimlane
focal: 编排者 lane 内的纵向编号主链
accent_budget: semantic-zones
source_facts:
  - 客户端发起刷新并接收展示数据
  - 编排者完成准入、查询、转换、候选汇聚与打包
  - 数据服务返回原始素材
  - 决策服务比较候选并返回选择
relationships:
  - 客户端 -> 编排者：刷新请求
  - 编排者 -> 数据服务：查询请求
  - 数据服务 -> 编排者：原始字段
  - 编排者 -> 决策服务：候选与特征
  - 决策服务 -> 编排者：选中结果
  - 编排者 -> 客户端：展示数据
main_chain: 准入 -> 查询 -> 转换 -> 候选池；选中结果回到打包
supporting_region: 单一素材失败不阻断其他合格候选
unknowns:
  - 真实接口名、同步 / 异步边界、具体判据与耗时
cuts:
  - 内部业务标识、真实 UI、未提供的数值和异常分支
```

没有门禁、候选池、输出高亮或页脚事实时删除对应槽位。不要为了填满模板补造失败路径、旁路或顺序。

## 信息结构与组件槽位

1. **角色分列，宽度随职责分配。** 常见为 3–5 条 lane；编排者通常更宽，因为主链步骤与加工说明最多。输入与出口可以收窄，不强制等宽或固定四列。更多角色优先拆图，不靠缩字硬塞。
2. **主链只在编排者 lane 内编号。** 编号表达阶段顺序；跨 lane 的请求、响应和外部处理不另起一套编号。客户端触发与展示也不强制编号。
3. **节点写动作与加工，边写交换内容。** 处理卡可包含「动作标题 / 关键转换 / 一句说明」；跨域边写「查询请求、原始字段、候选与特征、选中结果」等载荷，避免只写“调用”。
4. **请求与响应可分通道。** 本例让同一次交互的去线与回线使用不同 y 位置或独立折线路由；若另一种布线更适合当前内容，可以调整，只要真实方向与载荷仍然可读。箭头表达方向，线型或颜色只作辅助，标签不能压住短边和节点文字。
5. **返回线进入实际下一步。** 候选池编号在打包之前，不代表可以补一条“候选池 → 打包”直线；若事实必须经过决策，就由决策结果连回打包。没有来源依据时不增加旁路。
6. **辅助区域只承载新增边界。** 可放失败隔离、适用范围或口径说明；正文已经清楚或来源没有时省略。

| 槽位 | 内容 | 复核 |
|---|---|---|
| lane 标题 | 角色名；可选系统或接口短签 | 角色归属有来源，不用颜色代替文字 |
| 编号签 | 主链阶段序号 | 同一编号只指同一阶段 |
| 处理卡 | 动作标题 + 必要加工 / 说明 | 不把实体名称误当动作 |
| 跨域边标签 | 请求、响应或数据载荷 | 方向、交换内容与正文一致 |
| 终态 / 输出卡 | 打包结果或展示出口 | 不保证未被来源确认的选中结果 |
| 页脚注 | 失败隔离、边界或口径 | 不重复导语，不虚构异常路径 |

## 原生 SVG 实现

- 容器、处理卡、编号签和起止 / 数据节点优先使用 `rect / circle / ellipse / text`。角色名称是“决策服务”并不意味着它需要菱形；只有真实条件分支才使用判断形状。
- SVG 精排中的门禁可用带“准入 / 门禁”文字的圆角卡。必须使用原生菱形时改走 DSL；不要用会降级为图片的 `polygon` 冒充原生判断节点。
- 所有有向边使用 `data-role="edge"` 和 `marker-end`。禁止在线头另画三角图片；返回折线同样保留原生箭头。
- 标签跨不同浅底且需要统一底色时，可用小型原生 `rect` 衬底；不要以大胶囊覆盖短边。所有文字按实际底色声明 `data-bg`。
- 模板中的列宽、色板与节点文案都是变量。通用示例使用蓝 / 绿 / 紫区分职责，不表示状态、优劣或固定品牌。
- 原生 connector、`attached_object` 和客户端拖动是三层证据。转换后检查 raw；没有客户端实测时不声称整卡移动或连线跟随已验证。

## 可读性与验证

先按目标文档宽度删减文字，再确定坐标。主链卡保留短动作与关键转换，长接口说明移到正文。以 1600px 逻辑画布显示为 800px 为例，20–24px 文字只有 10–12px；必须用实际正文宽度复核，而不是只看放大 PNG。

独立通用样例：[orchestrator-swimlane.svg](../evals/fixtures/orchestrator-swimlane.svg)。它展示四条不等宽 lane、五阶段编排主链、数据与决策两组请求 / 响应，以及一条独立返回折线。

应用模板时，把 `diagram.svg` 替换为当前实际文件，检查的是用户产物而不是通用 fixture：

```bash
python3 scripts/fit_check.py diagram.svg --json
python3 scripts/lint_svg.py diagram.svg
npx -y @larksuite/whiteboard-cli@0.2.13 -i diagram.svg -f svg --check
npx -y @larksuite/whiteboard-cli@0.2.13 -i diagram.svg -f svg -o /tmp/diagram.png
```

维护通用 fixture 时，另跑其专属回归和共享检查矩阵；这些测试不替代上面的实际产物检查：

```bash
python3 tests/test_orchestrator_swimlane.py
python3 tests/test_article_pattern_fixtures.py
```

专属回归只固定当前示例：检查结构不降级为 `image/svg`、五个编号文本、10 条原生有向边及全部端点方向，包括数据服务内部处理和决策返回折线。样例的几何与通道不是用户图的必填规格；样例通过也不代表实际内容、客户端体验或拖动绑定自动通过。

### 2026-11-20 本地证据

当场 `fit_check.py` 无错误，保留 4 个外边距提示：本例采用约 64px 横向边距与紧凑标题 / 页脚节奏，已目视确认没有出血。`lint_svg.py` 无输出。固定版本 parser check 为 0 error、1 warning；唯一 warning 是“展示数据”的小型标签衬底有意横跨客户端与编排者 lane，已确认不是文字遮挡或无意互压。

转换得到 84 个节点、11 条 connector，其中 10 条是有向边，另一条是无向分隔线；没有 `image` / `svg` 降级。自动回归通过。已目视完整 PNG 与约 800px 宽缩放预览，未发现截断、文字互压或错误箭头；次级说明在默认宽度属于紧凑信息层，实际内容仍应优先删减。
