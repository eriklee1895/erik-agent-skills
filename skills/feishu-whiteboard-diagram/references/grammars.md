# 布局语法

先选关系，再选骨架。下面这些来自高质量飞书技术文档画板，以及社区 `feishu-whiteboard-pro` 的原型库（流水线分叉、泳道、枢纽、对比列、时间线、四象限、焦点+细节）。它们是语法，不是必须填空的模板；节点名称和数量由内容决定。

先用骨架表达关系，再自主选择适合文章的配色。明确的阅读层级和稳定间距比套用色板名称更重要；原型不要求唯一最大卡、固定颜色或固定页脚。图中的页脚只是可选位置，没有新增信息时省略。

画布建议：宽 1400–1600，外边距 64–80，分区间距 40–56，卡片内边距 20–28，有连线的缝 48–64。坐标和焦点规则见 [composition.md](composition.md)。

## 分层条带 — 「每层屏蔽什么」

**何时用：** 自下而上或自上而下的协议/系统分层；每层要同时讲清组件、职责、边界。

```
标题 + 一句分层方向（上/下行图例）
┌──────── L4 层名 ─────────────────────────────────────────┐
│  组件/协议          │  功能职责            │  边界        │
└──────────────────────────────────────────────────────────┘
     ↑ 上行 API 名                ↓ 下行 API 名
┌──────── L3 ...
页脚：一句话边界
```

要点：

- 各层**等宽**，内部三列（或两列）对齐成纵队，读者才能扫「职责 vs 边界」。
- 层间用短标签箭头写真实 API（`OpenStream`、`OnTrackOpen`）。上行 / 下行可用位置、标签、线型或不同颜色区分，遵循当前视觉契约。
- 层标签可以放在条带内左侧，不必用官方 DSL 的「标签在框外」——文档精排更紧。
- 非必要不在层内节点之间连线；分层本身已经表达调用方向。

## 任务循环 — 「谁决策、谁执行」

**何时用：** Agent / 工作流主循环；有「直接结束」和「调用工具再回填」两条路。

```
[用户任务] → [加载上下文] → [判断]
                    ↙ 直接回答          ↘ 需要工具
            [最终答案]              ┌── 工具回路 ────────┐
            短支，到此结束          │ [执行工具]→[工具结果] │
                                    │     ↑ 短虚线回填     │
                                    └─────────────────────┘
画布内页脚：角色分工一句
```

要点：

- 准备、判断和执行分支应可区分；可用描边盒、足够宽的判断形状、色带或文字层级，保证判断文字清楚。
- 工具回路可通过区域边界、留白、位置或放大建立层级；是否上色取决于文章与颜色角色。直接回答与工具回填两条关系都应清楚。
- 回填必须是虚线，接到判断，并写「结果回填」。虚线走分叉内部的短折线，**不要绕画布一圈**。

## 学习闭环 — 「值不值得写回去」

**何时用：** 执行 → 复盘 → 门禁 → 分类落盘 → 下次注入。

```
[任务完成] → [复盘] → ◆值得复用?◆ ─否─→ [结束]
                         │是
                    [写入门禁]
                 /     |     \
           USER.md  MEMORY  SKILL.md
                 \     |     /
                    [后续任务注入] → [复用执行] ···虚线下一轮···
```

要点：

- 上排只放门禁（完成 → 复盘 → 值得? → 否/结束）。
- **三种落盘是焦点**：三列对比，每列写满「写什么 / 何时读 / 门禁 / 风险」，不要从门禁拉出三根斜线迷宫，也不要三列空壳。
- 「否」必须有结束态。门禁写扫描 / 去重 / 质量。
- 「下一轮」用起点上的标签说明，不要绕场虚线。

## 对比列 — 「选项、差异或权衡」

**何时用：** 2–3 个选项逐项权衡。

列头和行对齐，方案默认同等视觉权重。来源明确给出优劣结论时，才突出相应格；中性比较可以统一浅底或协调系列色，不制造获胜项。

## 枢纽 — 「一个核心带 N 个方面」

**何时用：** Agent / 平台周围一圈能力。用核心位置与连接关系建立枢纽，尺寸按信息量调整；可用大小、留白或边界强调，不要求唯一饱和。

## 时间线 — 「阶段怎样推进」

**何时用：** 阶段、里程碑。轴 + 节点表达顺序；来源明确的关键阶段可用尺寸、标记或颜色强调，没有高潮时保持连续节奏。

## 多列运行架构 — 「请求向右，事件向左」

**何时用：** 宿主 / 传输 / 协调层 / 运行时这种列向职责，且存在往返。

```
  01 宿主          02 传输         03 协调         04 运行时
  请求向右 →
  [发起]  →  [Gate]  →  [Processor]  →  [Agent Loop]
                                         ↓ tools
  [投影]  ←  [Outbound] ← [Outbound] ←  [Events]
  事件向左 ←
页脚边界条：各列一句话
```

要点：

- 列名与职责形成共同对齐线，编号按需使用。容器与内卡可采用中性色、协调角色色或品牌色；职责主要靠标签、边界与位置区分，不要求各列异色。
- 请求链和事件链要在垂直位置上错开（上请求、下事件），避免箭头对撞。
- 若四列分工需要额外解释，可在辅助区域收束边界；列头和正文已清楚时省略。

## 编号层级 — 「中断后恢复什么」

**何时用：** 包含关系 + 每层一个恢复问题（thread / turn / item，或 session / request / event）。

```
标题：三层状态，三种恢复粒度          右上：一张图回答什么
┌ 01 THREAD 对话边界 ──────────────── 恢复哪段上下文？ ┐
│  [HISTORY] [FORK] [SUBSCRIBE]                         │
└──────────────── ↓ 一个 Thread 含多个 Turn ────────────┘
┌ 02 TURN 事务边界 ────────────────── 这次事务结束了吗？┐
│  inProgress → completed / interrupted / failed        │
└──────────────── ↓ 一次 Turn 产生多个 Item ────────────┘
┌ 03 ITEM 工作单元 ────────────────── 哪个动作到了哪？ ┐
│  USER | PLAN | COMMAND | FILE | AGENT                 │
└───────────────────────────────────────────────────────┘
页脚：threadId + turnId + itemId     Delta 是预览 · Completed 是事实
```

要点：

- `01` 色块贴在层容器左上角，允许轻微重叠，这是层级签，不是装饰。
- 右侧固定一列「问题」，强迫每层只回答一个恢复问题。
- 状态保持稳定、可解释的标记；例如进行蓝、成功绿、中断黄、失败红。也可适配品牌与文章色板，用文字或图标明确区分，不依赖颜色猜状态。
- 页脚给出恢复坐标，不要只重复层名。

## 泳道 — 「多角色怎么握手」

**何时用：** 用户 / Agent / 工具（或前端 / 网关 / 后端）共享一条时间轴。

左列写角色名，时间向右。可用协调角色色、标签和分隔线区分车道，按论点决定是否突出某次握手；等权角色可以保持相同重量。工具结果可用虚线回填。

## 四象限 — 「两个维度、四个去处」

**何时用：** 可复用 × 可验证、投入 × 影响这类决策。

两轴交叉成四格，保持坐标与尺度清楚。四区可等大；来源有明确推荐区域时再用标记、描边或局部强调，不为构图补造“获胜象限”。

## 焦点+细节 — 「一件大事带几条支持」

**何时用：** 内容其实只有一个主判断，却被画成了均等卡片墙。

左侧大卡 1.5–2× 右侧支持卡。大卡写结论，小卡写分支条件。

## 组合与拒绝

- 来源 → 分析 → 行动的多角色总览，使用 [语义分区价值链](semantic-columns.md)：主链、回流与直达同属一套价值流，来源明确的落地步骤可作为弱一档的底部辅助带。
- 一张图只用一种主语法。两套关系各自需要独立焦点和完整说明时，拆成两张画板。
- 不要为了「丰富」加侧边栏监控、emoji 墙、未出现在原文里的模块。
- 官方 DSL 架构骨架（标签在外、cylinder 数据库）适合基础设施图；协议/产品文档更接近上面 1 和 4。
