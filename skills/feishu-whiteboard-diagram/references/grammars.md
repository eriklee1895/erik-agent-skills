# 布局语法

先选关系，再选骨架。下面这些来自高质量飞书技术文档画板，以及社区 `feishu-whiteboard-pro` 的原型库（流水线分叉、泳道、枢纽、对比列、时间线、四象限、焦点+细节）。它们是语法，不是必须填空的模板；节点名称和数量由内容决定。

先用骨架表达关系，再自主选择适合文章的配色。明确的阅读层级和稳定间距比套用色板名称更重要；原型不要求唯一最大卡、固定颜色或固定页脚。图中的页脚只是可选位置，没有新增信息时省略。

布局与阅读层级见 [composition.md](composition.md)；字号、间距和显示宽度统一见 [visual-system.md](visual-system.md)。下列骨架按来源关系调整，不要求填满所有位置。

## 分层条带 — 「每层屏蔽什么」

**何时用：** 自下而上或自上而下的协议/系统分层；每层要同时讲清组件、职责、边界。

```
标题 + 一句分层方向（上/下行图例）
┌──────── L4 层名 ─────────────────────────────────────────┐
│  组件/协议          │  功能职责            │  边界        │
└──────────────────────────────────────────────────────────┘
     ↑ 上行 API 名                ↓ 下行 API 名
┌──────── L3 ...
页脚：一句话边界
```

要点：

- 各层**等宽**，内部三列（或两列）对齐成纵队，读者才能扫「职责 vs 边界」。
- 层间用短标签箭头写真实 API（`OpenStream`、`OnTrackOpen`）。上行 / 下行可用位置、标签、线型或不同颜色区分，遵循当前视觉契约。
- 层标签可以放在条带内左侧，不必用官方 DSL 的「标签在框外」——文档精排更紧。
- 层容器表达归属或抽象边界；只有来源明确的交互才加连线。上下排列本身不能证明调用方向。

## 任务循环 — 「谁决策、谁执行」

**何时用：** Agent / 工作流主循环；有「直接结束」和「调用工具再回填」两条路。

```
[用户任务] → [加载上下文] → [判断]
                    ↙ 直接回答          ↘ 需要工具
            [最终答案]              ┌── 工具回路 ────────┐
            短支，到此结束          │ [执行工具]→[工具结果] │
                                    │     ↑ 短虚线回填     │
                                    └─────────────────────┘
画布内页脚：角色分工一句
```

要点：

- 准备、判断和执行分支应可区分；可用描边盒、足够宽的判断形状、色带或文字层级，保证判断文字清楚。
- 工具回路可通过区域边界、留白、位置或放大建立层级；是否上色取决于文章与颜色角色。直接回答与工具回填两条关系都应清楚。
- 工具结果回填接到来源指定的处理节点；本原型回到判断，使用短虚线并标「结果回填」。已有线型约定优先，反馈不绕无关区域。

## 学习闭环 — 「值不值得写回去」

**何时用：** 执行 → 复盘 → 门禁 → 分类落盘 → 下次注入。

```
[任务完成] → [复盘] → ◆值得复用?◆ ─否─→ [结束]
                         │是
                    [写入门禁]
                 /     |     \
           USER.md  MEMORY  SKILL.md
                 \     |     /
                    [后续任务注入] → [复用执行] ···虚线下一轮···
```

要点：

- 上排只放门禁（完成 → 复盘 → 值得? → 否/结束）。
- 当来源确有三类落盘目标时，用对齐的对比列说明「写什么 / 何时读 / 门禁 / 风险」中已知且相关的项。目标数量与列内内容按事实选择，不为填满三列补造规则。
- 「否」必须有结束态。门禁写扫描 / 去重 / 质量。
- 「下一轮」用起点上的标签说明，不要绕场虚线。

## 闸门流水线 — 「达标即停，逐段加码」

**何时用：** 多级处理逐级加码（先便宜后昂贵），任一级达标即提前出口；如分级压缩、逐级校验、分阶段重试。

```
                    ┌──── 出口带：达标后正常流转 ────┐
                    ↑ 达标        ↑ 达标        ↑ 达标
[入检] → [L1 便宜手段] → [L2 中等手段] → [L3 昂贵手段]
                                      │仍不满足
                                  [受控错误 / 降级]
```

要点：

- 出口带放主链上方或右侧，收集各级「达标」边；主链继续向下的边标「仍超限」等否定条件，两种分支标签成对出现、靠近各自分叉。
- 各级卡片共用「编号 + 名称 + 一句手段 + 何时进入」节奏；终止条件集合（如若干停止条件）可另成编号小卡区，用左色条卡列出，见 [成套技术图](technical-article-figures.md#常用组件标题带左色条卡类型签与终态卡) 的组件。
- 末端必须有兜底终态（受控错误、降级或人工），不让失败路径悬空；兜底与出口带用状态色区分（如失败红 / 成功绿，随当前视觉系统取值）。
- 级别数量由来源决定，两级达标即停同样成立；来源没有提前出口或兜底语义时，改用普通流水线表达，不为套骨架补造分支。

## 条件分流路由 — 「按什么判据走哪条路」

**何时用：** 需求分级、任务路由、风险分流；不同路线可以汇合，失败后也可能返回不同前序节点。

```
                         ┌─ 判据 A → [路线 A] ─┐
[输入] → [分析 / 路由] ──┤                     ├→ [共同后续]
                         └─ 判据 B → [路线 B] ─┘
                              ↑──── 失败原因，返回指定节点 ────
```

- 判据放在对应分支或分支卡内，不只写「是 / 否」。判据可能重叠时说明优先级或组合规则，不暗中假设互斥。
- 合流点说明后续为何可以共用；两条路线仍有差异时，不为整齐强行合并。
- 回流可用独立通道和虚线，标注触发原因与返回目标。来源没有兜底或回流时删去，不补造循环。
- 原生有向边保留方向；路由判据是文字事实，不用菱形图片代替说明。

独立通用样例：[conditional-routing.svg](../evals/fixtures/conditional-routing.svg)。

## 对比列 — 「选项、差异或权衡」

**何时用：** 2–3 个选项逐项权衡。

列头和行对齐，方案默认同等视觉权重。来源明确给出优劣结论时，才突出相应格；中性比较可以统一浅底或协调系列色，不制造获胜项。

## 枢纽 — 「一个核心带 N 个方面」

**何时用：** Agent / 平台周围一圈能力。用核心位置与连接关系建立枢纽，尺寸按信息量调整；可用大小、留白或边界强调，不要求唯一饱和。

## 代表实例扇出 — 「一个如何管理许多」

**何时用：** 一个编排者管理多个同类实例，每个实例又有相似的内部结构。目标是表达多重性与代表关系，而不是复制卡片墙。

```
[团队编排者] ─┬→ [实例 A]
              ├→ [实例 B] ···展开 B···→ [Worker 1 / 2 / …Y]
              └→ [实例 C…N]
```

- 用 `C…N`、`1:X:Y` 或「其余同类」明确表示折叠；展开符不是执行箭头，可用标签或虚线导航，与执行边区分。
- 只展开能代表差异或内部机制的实例。不同实例的关键差异不能用省略号抹掉，未知类别也不能凭整齐补齐。
- 详图沿用原实例名称或编号，让读者能回到总览中的来源。完整示例见 [总览与局部展开](technical-article-figures.md#总览--局部展开同一节点两种粒度)。

## 时间线 — 「阶段怎样推进」

**何时用：** 阶段、里程碑。轴 + 节点表达顺序；来源明确的关键阶段可用尺寸、标记或颜色强调，没有高潮时保持连续节奏。

## 多列运行架构 — 「请求向右，事件向左」

**何时用：** 宿主 / 传输 / 协调层 / 运行时这种列向职责，且存在往返。

```
  01 宿主          02 传输         03 协调         04 运行时
  请求向右 →
  [发起]  →  [Gate]  →  [Processor]  →  [Agent Loop]
                                         ↓ tools
  [投影]  ←  [Outbound] ← [Outbound] ←  [Events]
  事件向左 ←
页脚边界条：各列一句话
```

要点：

- 列名与职责形成共同对齐线，编号按需使用。容器与内卡可采用中性色、协调角色色或品牌色；职责主要靠标签、边界与位置区分，不要求各列异色。
- 请求链和事件链要在垂直位置上错开（上请求、下事件），避免箭头对撞。
- 若四列分工需要额外解释，可在辅助区域收束边界；列头和正文已清楚时省略。

## 编号层级 — 「中断后恢复什么」

**何时用：** 包含关系 + 每层一个恢复问题（thread / turn / item，或 session / request / event）。

```
标题：三层状态，三种恢复粒度          右上：一张图回答什么
┌ 01 THREAD 对话边界 ──────────────── 恢复哪段上下文？ ┐
│  [HISTORY] [FORK] [SUBSCRIBE]                         │
└──────────────── ↓ 一个 Thread 含多个 Turn ────────────┘
┌ 02 TURN 事务边界 ────────────────── 这次事务结束了吗？┐
│  inProgress → completed / interrupted / failed        │
└──────────────── ↓ 一次 Turn 产生多个 Item ────────────┘
┌ 03 ITEM 工作单元 ────────────────── 哪个动作到了哪？ ┐
│  USER | PLAN | COMMAND | FILE | AGENT                 │
└───────────────────────────────────────────────────────┘
页脚：threadId + turnId + itemId     Delta 是预览 · Completed 是事实
```

要点：

- `01` 色块贴在层容器左上角，允许轻微重叠，这是层级签，不是装饰。
- 右侧固定一列「问题」，强迫每层只回答一个恢复问题。
- 状态保持稳定、可解释的标记；例如进行蓝、成功绿、中断黄、失败红。也可适配品牌与文章色板，用文字或图标明确区分，不依赖颜色猜状态。
- 页脚给出恢复坐标，不要只重复层名。

## 泳道 — 「多角色怎么握手」

**何时用：** 用户 / Agent / 工具（或前端 / 网关 / 后端）共享一条时间轴。

左列写角色名，时间向右。可用协调角色色、标签和分隔线区分车道，按论点决定是否突出某次握手；等权角色可以保持相同重量。工具结果可用虚线回填。

## 四象限 — 「两个维度、四个去处」

**何时用：** 可复用 × 可验证、投入 × 影响这类决策。

两轴交叉成四格，保持坐标与尺度清楚。四区可等大；来源有明确推荐区域时再用标记、描边或局部强调，不为构图补造“获胜象限”。

## 焦点+细节 — 「一件大事带几条支持」

**何时用：** 内容其实只有一个主判断，却被画成了均等卡片墙。

可从左侧主卡约为右侧支持卡 1.5–2 倍宽起步，按文字和论点调整。主卡写判断，支持卡放证据或分支条件；若内容本来等权，改用对比列。

## 处境—矛盾—行动 — 「为什么现在必须改变」

**何时用：** 技术文章开篇需要同时交代外部压力、内部落差和必要行动。它是叙事构图，不是两个方案的优劣比较。

```
┌──── 处境 / 压力 ────┐   ┌──── 核心矛盾 ────┐
│ 目标、约束、典型工作 │   │ 当前落差及其影响 │
└────────────────────┘   └──────────────────┘
┌──────────── 来源支持的必要行动 / 结论 ────────────┐
```

两区可以不同宽，可按论点把核心矛盾作为重心；底部结论带只在有新增信息时保留。没有数值和共同尺度时，用文字、标记或明确的定性示意表达「快 / 慢」「高 / 低」，不用无刻度长短条暗示精确比例。

## 资产目录 — 「有哪些可复用能力」

**何时用：** 工具、Skill、模板、知识资产或交付物清单。分类依据优先选择研发环节或用户结果，而不是按视觉颜色随意分组。

```
[分类 A]                    [分类 B]
[名称｜用途｜产物形态]       [名称｜用途｜产物形态]
[名称｜用途｜产物形态]       [名称｜用途｜产物形态]
```

同类资产复用名称、说明和形态标签的对齐线；各组数量可以不同，可让外框共顶建立节奏，内部不为填满留白而补造资产。目录本身不表示流程，只有来源明确的依赖或先后顺序才加箭头。

诊断链也可复用这种重复卡思路：每个环节按「瓶颈 → 核心影响 → 优先级」组织，优先级有来源和图例，底部用一句话归纳跨环节共同问题；不把五列等结构固定成模板。

## 组合与拒绝

- 共享输入、双模块协同、跨层数据 / 控制和阶段到指标映射见 [成套技术图](technical-article-figures.md)。
- 来源 → 分析 → 行动的多角色总览，使用 [语义分区价值链](semantic-columns.md)：主链、回流与直达同属一套价值流，来源明确的落地步骤可作为弱一档的底部辅助带。
- 一张图保持一个主要阅读任务；主结构与辅助面板可以组合。两套关系各自需要完整说明时，拆成两张画板。
- 不要为了「丰富」加侧边栏监控、emoji 墙、未出现在原文里的模块。
- 官方 DSL 架构骨架（标签在外、cylinder 数据库）适合基础设施图；协议/产品文档更接近上面 1 和 4。
